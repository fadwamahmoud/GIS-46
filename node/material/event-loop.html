What the heck is
the event loop?

An intuitive guide to how JavaScript actually runs — call stacks, Web APIs, callbacks, and why none of it blocks.

The Problem

Words we use but often don't fully understand

Single-threaded — JavaScript can only do one thing at a time.

Non-blocking — and yet, it somehow doesn't freeze while waiting for things.

Asynchronous / callback — code that runs later, not now, when something is ready.

Concurrency — multiple things making progress, even though there's only one thread.

Philip Roberts' point: most of us nod along to these words without really knowing what they mean. This talk gives you the mental model to actually understand them.

Under the Hood

The JavaScript runtime (V8)

Heap

Where memory is allocated. Objects, variables, functions — all stored here. Mostly unstructured.

Not what the talk focuses on — the stack is what matters for understanding async.

Call Stack

Where JavaScript tracks what it's currently doing. When you call a function, it gets pushed on. When it returns, it gets popped off.

One stack. One thread. One thing at a time.

Surprise: setTimeout, DOM events, HTTP requests — none of these are in V8. They are provided by the browser (or Node.js), not the JavaScript runtime itself.

The Call Stack

Last In, First Out — like a stack of plates

Call a function → it gets pushed onto the top of the stack.

Function returns → it gets popped off the top. Whatever was underneath resumes.

When you see a stack trace in an error, you're literally seeing the state of the call stack at the moment it crashed.

Call a function that calls itself forever → stack overflow. The stack runs out of space.

The Problem

What happens when the stack is blocked?

If a function is slow (network call, image processing, big loop), it sits on the stack until it finishes.

While it's on the stack, nothing else can run. The browser can't re-render. Clicks don't register. The page freezes.

A synchronous network request that stalls means the entire browser locks up until it completes (or times out).

This is exactly why "don't block the event loop" is such common advice. Anything slow on the stack = frozen UI.

The Solution

The browser is more than just the JavaScript runtime

Web APIs — provided by the browser (or Node.js). Handle timers, network requests, DOM events — outside the JS stack.

Callback Queue — when a Web API finishes, it puts your callback here to wait its turn.

Event Loop — checks: "is the stack empty?" If yes, it moves the first item from the queue onto the stack to run.

These three pieces work together to give JavaScript concurrency without threads. The JS runtime is still single-threaded — the browser does the heavy lifting in parallel.

The Full Picture

How all the pieces connect

Async in Action

What happens when you call setTimeout?

console.log('Hi'); setTimeout(function cb() { console.log('there'); }, 5000); console.log('JSConfEU');

console.log('Hi') — pushed onto stack, runs immediately, popped off. Prints "Hi".

setTimeout(cb, 5000) — pushed onto stack, then handed off to the browser's timer API. Popped off immediately — done.

console.log('JSConfEU') — pushed, runs, popped. Prints "JSConfEU". Stack is now empty.

5 seconds later — browser timer fires. cb() pushed into the callback queue. Event loop sees empty stack → pushes cb onto stack. Prints "there".

A Useful Trick

setTimeout with a delay of zero

setTimeout(function() { console.log('B'); }, 0); console.log('A'); // Output: A then B

Zero doesn't mean "run immediately" — it means run as soon as the stack is empty. The callback still goes through the queue.

setTimeout is a minimum delay, not a guaranteed one. The browser has a minimum of about 4ms even if you pass 0.

The trick is useful to defer something until after the current stack finishes — letting the browser render, for example.

Key Rule

Don't block the event loop

Blocked stack = frozen UI

The browser tries to repaint the screen every ~16ms (60fps). But it can't repaint while your code is on the stack.

Slow synchronous code → UI stutters or completely freezes. Users click, nothing happens.

Async = UI stays responsive

Move slow work into async callbacks (fetch, setTimeout, event handlers). The stack stays free, and the browser can keep rendering in between callbacks.

This is the entire reason async exists in JavaScript.

Scroll handlers are a classic trap — they fire many times per second. If your handler does slow work, you flood the callback queue and block the event loop. Solution: debounce them.

The Browser's Render Queue

Rendering is also queued — and can be blocked

The browser has a render queue in addition to the callback queue. It tries to repaint every 16ms.

The event loop treats renders with higher priority than callbacks, but it still can't render while the stack is busy.

A slow synchronous loop running for 5 seconds means no renders for 5 seconds. The user sees a frozen page.

Async code yields control back to the event loop between callbacks — giving the browser a chance to render between each one.

Callbacks

Two meanings of "callback"

Any function passed to another

Broad definition. Any function you pass as an argument is technically a callback.

[1,2,3].forEach(n => console.log(n));
// the arrow fn is a callback

An async callback

Narrower definition. A function handed off to a Web API that will be pushed to the callback queue in the future.

setTimeout(() => doThing(), 1000);
// this is an async callback

In the context of the event loop, "callback" usually means the async kind — a function waiting in the queue to be run when the stack is free.

In Node.js

The same model — different provider

Node.js uses the same V8 engine and the same call stack + event loop + callback queue model.

Instead of browser Web APIs, Node provides core modules (fs, http, crypto…) that run their slow work in background C++ threads.

When a Node operation finishes (file read, network response), its callback is pushed to the same kind of callback queue. The event loop moves it to the stack.

This is how Node handles thousands of simultaneous connections on a single thread — it never waits, it just queues.
