Part 1

Introduction to Frameworks

What they are, what they solve, and how to choose one

Frameworks · Dev.to

Every web app needs the same things

Every time you build a new app, you'd have to write the same boilerplate again: routing, database access, user sessions, security, templating…

You'd also need to make hundreds of architectural decisions from scratch: how to organise files, how to handle errors, how to structure your code.

And if you're on a team, every developer would do things slightly differently — making the codebase hard to navigate and maintain.

Frameworks exist because there's no need to reinvent the wheel. They batch up the recycled code every app needs and give it to you for free — so you can focus on the features that are actually unique to your product.

Frameworks · MDN

What a web framework actually does for you

URL Routing

Maps incoming URLs to the right handler function. Supports URL parameters, query strings, and HTTP verbs (GET, POST, etc.).

Database Access

Provides a unified API to read and write from a database. Many use an ORM so you work with objects, not raw SQL.

Templating

Inserts dynamic data into HTML templates to generate pages on the fly.

Sessions & Auth

Manages user login, sessions, cookies and access control — without you building it from scratch.

Security

Handles common vulnerabilities: XSS, CSRF, SQL injection. Gives you safe defaults out of the box.

Structure

Forces consistent organisation (e.g. MVC). Other developers know where to find things immediately.

Frameworks · Dev.to

Framework vs library — what's the difference?

Library

A collection of functions you call when you need them. You are in control — you decide when and how to use it. You provide the overall structure yourself.

Examples: lodash, axios, date-fns

Framework

A skeleton that calls your code. You fill in the blanks — the framework dictates the overall structure and flow. You plug into it.

Examples: Express, Django, Rails, Laravel

Under the hood, frameworks are just code libraries — open source code written by other developers. The key difference is who's in charge: with a library, you call it; with a framework, it calls you.

Frontend (JS)

Frameworks · MDN

How do you choose a framework?

Effort to learn — How steep is the learning curve? Does it have good documentation and an active community?

Productivity — How quickly can you build something? Opinionated frameworks (Rails, Django) are often faster to start with.

Performance — Does it handle the load your app needs? Some frameworks are better suited for high-concurrency or real-time use.

Language you already know — If you know JavaScript, start with Express. There's no benefit learning a new language and a new framework at once.

Community and ecosystem — A larger community means more packages, more answered questions on Stack Overflow, and more tutorials.

Part 2

Introduction to Express

Setting up a server, handling requests, and understanding middleware

Express

What is Express?

Express is a minimal, unopinionated web framework for Node.js. It handles the repetitive plumbing of building a server so you don't have to.

Remember the raw http.createServer() code from Chapter 3? Express wraps that and makes routing, responding, and extending your server far cleaner.

It's intentionally barebones — you start with almost nothing and add only the features you need via middleware and packages.

It's the most widely used Node.js framework. Almost every Node tutorial, job description, and project you'll encounter will use or reference it.

Express · Setup

Setting up Express from scratch

terminal
$ mkdir my-app && cd my-app
$ npm init -y
Wrote to /my-app/package.json
$ npm install express
added 65 packages in 1.2s

npm init -y creates a package.json with sensible defaults. The -y skips all the prompts.

npm install express downloads Express and saves it to your dependencies. A node_modules/ folder is created automatically.

Now create an app.js file in the project root — that's where your server code lives.

Express · Setup

Your first Express server

// app.js const express = require("express"); const app = express(); app.get("/", (req, res) => res.send("Hello, world!")); const PORT = process.env.PORT || 3000; app.listen(PORT, (error) => { if (error) throw error; console.log(`Listening on port ${PORT}!`); });

require("express") imports the framework, then we call it as a function to create our app object.

app.get("/",...) registers a route — "when a GET request arrives at /, run this function".

app.listen(PORT, ...) starts the server. The if (error) throw error is important — without it, startup errors fail silently.

Express · Setup

Running your Express server

terminal
$ node app.js
Listening on port 3000!
# Or with auto-restart on file changes:
$ node --watch app.js
Listening on port 3000!

Open a browser and visit http://localhost:3000/ — you should see Hello, world!

The --watch flag (built into Node) auto-restarts the server when you save any file. No more manually stopping and restarting after every change.

You may also see nodemon used for this in older tutorials — it does the same thing. Stick with --watch for new projects.

When Express receives the request, it finds the first route that matches both the HTTP verb and the path. Order matters — routes are checked top to bottom.

Express · Request & Response

The req and res objects

req — request object

Everything about the incoming request. Express parses it and stores it here.

req.method // 'GET', 'POST' req.path // '/about' req.params // URL params req.query // ?key=value req.body // POST body req.headers // HTTP headers

res — response object

How you send data back to the browser. Always call one of these to end the cycle.

res.send('text') // send string res.json({}) // send JSON res.sendFile(path) // send a file res.redirect('/x') // redirect res.status(404) // set status code .send('Not found')

Express · Middleware

What is a middleware function?

A middleware function is any function that receives req, res, and a third argument next. It can inspect or modify the request, then either respond or call next() to pass it along.

In Express, every request passes through a chain of middleware functions one by one until something responds.

Your route handlers (app.get(...)) are themselves middleware — they just happen to be the last in the chain for a given route.

// A simple middleware function function logger(req, res, next) { console.log(`${req.method} ${req.path}`); next(); // pass to the next function in the chain } app.use(logger); // apply to all routes

Express · Middleware

The middleware chain in action

1

Request arrives — Express creates req and res objects and starts the chain.

↓
2

Global middleware (e.g. logger, body parser, auth check) — runs on every request. Calls next() to continue.

↓
3

Route matching — Express finds the first route whose verb and path match the request.

↓
4

Route handler — your function runs. It calls res.send(), res.json(), etc. to end the cycle.

If no route matches, Express falls through to the end. Always add a catch-all or error handler to return a proper 404 rather than leaving the browser hanging.

Express · Routing

Adding multiple routes

const express = require("express"); const app = express(); app.get("/", (req, res) => { res.send("<h1>Home</h1>"); }); app.get("/about", (req, res) => { res.send("<h1>About</h1>"); }); app.get("*", (req, res) => { res.status(404).send("<h1>404 – Not Found</h1>"); }); app.listen(3000);

"*" is a wildcard — it matches any path. Put it last so it only catches requests that didn't match any earlier route. This is your 404 handler.

Express · Best Practice

Always get PORT from an environment variable

Avoid — hardcoded port
const PORT = 3000; app.listen(PORT);
Prefer — env var with fallback
const PORT = process.env.PORT || 3000; app.listen(PORT);

If process.env.PORT is set (by a deployment platform like Heroku or Railway), the app uses that. Otherwise it falls back to 3000 locally.

This way you can change the port without touching source code — just change the environment variable.

Express · Why It Matters

Raw Node vs Express — same result, very different code

Raw Node http module
const http = require('http'); http.createServer((req, res) => { res.writeHead(200, { 'Content-Type':'text/html' }); if(req.url === '/'){ res.end('Home'); } else if(req.url === '/about'){ res.end('About'); } else { res.writeHead(404); res.end('Not found'); } }).listen(3000);
Express
const express = require('express'); const app = express(); app.get('/', (req, res) => res.send('Home') ); app.get('/about', (req, res) => res.send('About') ); app.get('*', (req, res) => res.status(404).send('Not found') ); app.listen(3000);
