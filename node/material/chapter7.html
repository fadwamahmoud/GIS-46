Core idea

What does a controller do?

Controller = middleman

It decides what to do when a request arrives.

Talks to the model

It asks the model for data, but lets the model do the heavy lifting.

Talks to the view

It chooses what should be rendered or returned, but lets the view build the final HTML or JSON output.

Incoming request
→
Controller
→
Ask model
→
Send response

A controller is really just a function with well-defined responsibilities inside MVC.

The controller is the “brains” of the request.

Response methods

Ways a controller can respond

res.send

General-purpose response method.

Can send text, objects, arrays, and more.

res.json

Explicitly sends JSON.

Useful when building APIs.

res.redirect

Sends the client to a different URL.

Useful after actions like form submissions.

res.render

Renders a view template into HTML.

Common in server-rendered apps.

res.status

Sets the status code.

Usually chained like res.status(404).send(...).

Key rule

Set status first, then send the response.

res.status(404).send("Not found")
These are the main tools controllers use to answer requests.
3 / 11
JSON responses

res.send vs res.json

res.send

  • Flexible and general-purpose.
  • Can send many data types.
  • Sometimes handles objects as JSON automatically.

res.json

  • Always sends JSON.
  • More explicit and convenient for APIs.
  • Usually clearer when the response is meant to be JSON.

Simple rule of thumb: if you are sending JSON, use res.json.

Use the method that clearly matches your intent.
4 / 11
Important gotcha

Sending a response does not stop the function

app.use((req, res) => { res.send("Hello"); console.log("will still run!!"); res.send("Bye"); });
Why this is a problem
  • res.send() ends the request-response cycle.
  • But the rest of the function still keeps executing.
  • Trying to send again causes an error.
if (!author) { res.status(404).send("Author not found"); return; }

Use return after early responses when needed.

Responding once is not the same as exiting the function.

Because order matters, middleware that changes the request object is often placed near the top of the app.

Application-level

Bound to an instance of Express.

Registered with app.use() or app.METHOD().

Body parsers (e.g. express.json, express.urlencoded) - These allow us to correctly parse the incoming request’s body, so that we can use it through req.body

Router-level

Bound to an instance of Express Router.

Registered with router.use() or router.METHOD().

If something should happen first, register it first.

Controllers vs Middleware

Controllers

controllers are just functions.

controller and middleware are distinct concepts.

Controllers are a key component of the MVC and Middleware in Express allow you to run code, modify requests, or end the cycle in the request-response cycle

So we are using middleware in Express to implement the “Controller” part of the MVC pattern

Controller + route

async function getAuthorById(req, res) { const { authorId } = req.params; const author = await db.getAuthorById(Number(authorId)); if (!author) { res.status(404).send("Author not found"); return; } res.send(`Author Name: ${author.name}`); }
The controller reads params, calls the DB function, then responds.
8 / 11
Handling errors

Two ways to deal with async errors

Option 1: try/catch
try { const author = await db.getAuthorById(Number(authorId)); res.send(`Author Name: ${author.name}`); } catch (error) { res.status(500).send("Internal Server Error"); }
Option 2: throw and let error middleware handle it
app.use((err, req, res, next) => { console.error(err); res.status(500).send(err.message); });

Error middleware must have four parameters: (err, req, res, next).

Centralized error handling keeps controllers cleaner.
9 / 11
Custom errors

How to return better status codes

Create a custom error

class CustomNotFoundError extends Error { constructor(message) { super(message); this.statusCode = 404; this.name = "NotFoundError"; } }

Use it in the controller

if (!author) { throw new CustomNotFoundError("Author not found"); } app.use((err, req, res, next) => { res.status(err.statusCode || 500).send(err.message); });

Now your error handler can send 404 for missing data and 500 for unexpected errors.

Custom errors make the error middleware smarter.
