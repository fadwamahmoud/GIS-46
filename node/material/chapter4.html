Chapter 4 · Node.js for Beginners

Environment
Variables

How to configure your app differently across machines, store secrets safely, and never hardcode sensitive values again.

The Concept

Every machine your code runs on is a different environment

Your laptop during development — one environment.

A server on Netlify or Vercel when deployed — a different environment.

A colleague's machine — yet another environment.

Each environment has its own tools, configurations, and secret values. You need a way to pass those values to your app without baking them into the source code.

Think of it like a function with parameters. You call the same function with different arguments in different situations. Environment variables are the parameters for your entire application.

Environment Variables

What are environment variables?

Environment variables are key-value pairs available to a running process. They are set in the environment, not inside your code.

They let you provide different values for different environments — dev vs production — without touching source code.

They are the standard place to store secrets: database URLs, passwords, API keys — anything you must not commit to Git.

Without env vars

Secrets are hardcoded in source files. Anyone with repo access can read them. Changing a value means changing code and redeploying.

With env vars

Secrets live outside the code. The same codebase runs with different config in dev vs prod. Change a value without touching code at all.

Environment Variables

What you'll use them for in practice

NODE_ENV — the most common env var. Set to "development" or "production" so your app behaves differently in each context (extra logging, error details, etc.).

Database credentials — your local dev database URL and password vs the live production database. Never the same, never in your code.

API keys — third-party services (payment processors, email APIs, maps). They must stay secret.

PORT — the port your server should listen on. Deployment platforms often set this for you automatically.

Environment Variables

Naming convention — UPPER_SNAKE_CASE

The convention is UPPER_SNAKE_CASE — all capitals, words separated by underscores. This is sometimes called SCREAMING_SNAKE_CASE.

Valid names contain only letters, digits, and underscores, and cannot begin with a digit.

Invalid: names starting with a number (1_VAR), containing hyphens (my-var), spaces (my var), or special characters (VAR_#1).

Part 1

Loading Environment Variables

Three ways to get env vars into your running app

Loading · Method 1

Inline in the terminal command

terminal
$ NODE_ENV=prod DB_URL="postgres://localhost/mydb" node index.js

Variables are defined before the node command on the same line. They are available only for that one run.

Downside: quickly gets unwieldy with many variables. Sensitive values like passwords are visible in your shell history.

Quoting is optional for simple values, but required for values containing spaces or special characters like =.

Loading · Method 2

Using the shell's export command

terminal
$ export NODE_ENV=prod API_KEY="abc123"
$ node index.js
# In a NEW terminal tab:
$ node index.js
→ NODE_ENV is undefined here — new shell, fresh environment

export saves variables into the current shell session. All subsequent commands in that shell can read them.

Downside: variables are lost when you close the terminal. A new shell tab starts completely fresh. Run printenv to see all current variables.

Loading · Method 3 (recommended)

The .env file

.env# Comments start with # NODE_ENV=development PORT=3000 DB_URL="postgres://localhost/mydb" API_KEY="abc-super-secret-123"
terminal
$ node --env-file=.env index.js
Server running on port 3000
# Optional flag if file may not exist:
$ node --env-file-if-exists=.env index.js

All variables in one place, persists across sessions, easy to edit. The --env-file flag (built into Node since v20.6) loads it automatically.

Pass multiple --env-file flags for layered configs — later files override earlier ones.

.env File Syntax

What you can put in a .env file

Syntax
Example and result
Plain value
PORT=3000 → value is the string "3000"
Quoted value
NAME="my app" → quotes are stripped, value is my app
Single quotes
KEY='abc123' → also valid, quotes stripped
Comment
# This is a comment → ignored entirely
Multiline
MSG="line one\nline two" → \n becomes a real newline
export keyword
export PORT=3000 → the export is ignored, works the same

If the same variable is defined both in the shell environment and in the .env file, the shell environment value takes precedence. The .env file does not override what's already set.

Third-party Option

The dotenv package — you'll see this in the wild

Before Node had built-in --env-file support, the dotenv npm package was the standard way to load .env files.

Many existing projects and tutorials still use it. The concept is identical — same .env file format, same process.env access.

To use it: npm install dotenv, then call require('dotenv').config() at the top of your entry file.

With dotenv (older approach)
require('dotenv').config(); // now process.env is populated console.log(process.env.PORT);
Built-in Node (modern approach)
# terminal node --env-file=.env index.js # no extra package needed # process.env is already loaded

For this course, use the built-in --env-file flag. But recognise dotenv when you see it — the result is the same.

Part 2

Accessing Environment Variables

Reading them inside your Node.js code

Accessing Variables

process.env — the object that holds them all

Node's built-in process object represents the current running process. Its process.env property is a plain object containing every environment variable loaded for this session.

Access any variable like a regular object property: process.env.MY_VAR.

If the variable isn't set, the value will be undefined — always check before relying on it.

// Reading environment variables in your app console.log(process.env.NODE_ENV); // "development" or "production" console.log(process.env.PORT); // "3000" console.log(process.env.API_KEY); // "abc-super-secret-123" console.log(process.env.NOT_SET); // undefined

Accessing Variables

Using env vars to change behaviour

// index.js — loaded with: node --env-file=.env index.js const http = require('http'); const PORT = process.env.PORT || 3000; const isDev = process.env.NODE_ENV === 'development'; http.createServer((req, res) => { if (isDev) { console.log(`[DEV] ${req.method} ${req.url}`); } res.end('Hello!'); }).listen(PORT, () => { console.log(`Server running on port ${PORT}`); });

|| 3000 is a fallback — if PORT isn't set, default to 3000. This is a very common pattern.

Important Gotcha

Environment variables are always strings

No matter what you put in the .env file, Node always reads it as a string. There are no numbers or booleans — only strings.

If you need a number or boolean, you must convert it yourself after reading it.

WRONG — this is a bug
# .env PORT=3000 DEBUG=true // index.js const port = process.env.PORT; // port === "3000" (string!) if (process.env.DEBUG) { // ALWAYS runs — "false" is truthy! }
RIGHT — convert explicitly
# .env PORT=3000 DEBUG=true // index.js const port = Number(process.env.PORT); // port === 3000 (number) const debug = process.env.DEBUG === 'true'; // debug === true (boolean)
Part 3

Keeping Secrets Safe

The rules that matter most when using env vars

Security

Never commit your .env file to Git

This is the single most important rule. If your .env file contains database passwords or API keys and you push it to a public GitHub repo, those secrets are immediately exposed — to the whole internet, forever, even if you delete the file later.

Add .env to your .gitignore file on day one, before writing a single secret into it.

Create a .env.sample file with placeholder values — commit that instead, so teammates know which variables are needed.

.gitignore — add this
# Environment variables .env .env.local .env.*.local
.env.sample — commit this
# Copy to .env and fill in values NODE_ENV=development PORT=3000 DB_URL=your_database_url_here API_KEY=your_api_key_here

Deployment

How environment variables work when you deploy

When you deploy, your repo won't contain your .env file — it's gitignored. The deployment platform needs to know your variables another way.

Every major platform (Netlify, Vercel, Railway, Render, Heroku…) has a dashboard UI where you set environment variables. They get injected into your app at runtime.

Your production npm start script should run just node index.js — without the --env-file flag, since the platform provides the variables directly.

Best Practice

Document your environment variables

Anyone who clones your repo needs to know which variables to set before the app will run. Document them.

Add a section to your README.md listing each variable, what it does, whether it's required, and an example value.

Include a .env.sample in the repo with dummy values. Anyone cloning the repo can copy it to .env and fill in real values.

## README.md — Environment Variables section ### Required environment variables | Variable | Description | Example | |-------------|--------------------------------|-----------------------| | NODE_ENV | Runtime environment | development | | PORT | Port the server listens on | 3000 | | DB_URL | PostgreSQL connection string | postgres://localhost/ | | API_KEY | Third-party API authentication | (get from provider) | Copy `.env.sample` to `.env` and fill in your values.

Putting It All Together

The complete env var workflow

Step 1: Add .env to .gitignore immediately when starting a project.

Step 2: Create a .env file with your local values. Create a .env.sample with placeholder values and commit that.

Step 3: Run your dev server with node --env-file=.env index.js.

Step 4: Access values in code via process.env.VARIABLE_NAME. Convert types as needed.

Step 5: When deploying, set variables in the platform's dashboard. Production script runs node index.js with no --env-file.

Step 6: Document all variables in your README and .env.sample.
